# AGENTS.md

Instructions for AI coding agents (Claude Code, Codex, Cursor, or any other LLM-based tool) working in this repository.

## What this is

SECourses Musubi Trainer — a Gradio GUI (`musubi_tuner_gui/`) wrapping the vendored `musubi-tuner` training backend (`musubi-tuner/`) to train LoRAs and full fine-tunes for Qwen Image, Qwen-Image 2.1, Wan 2.1/2.2, FLUX / FLUX.2 / FLUX Klein, Z-Image, Ideogram 4, Krea 2, ERNIE-Image, Mage-Flow / Mage-Flow-Edit, HiDream-O1, LTX 2.3, MiniMax H3, and Kandinsky 6. `README.md` is the user-facing feature tour (screenshots, install instructions, marketing); this file and `AI_TRAINER_GUARDRAILS.md` are for people/agents changing the code.

## Read this before adding a new trainer tab or model

**`AI_TRAINER_GUARDRAILS.md` documents mistakes already made once in this codebase and fixed — read it before adding or modifying a trainer tab.** They're easy to reintroduce when copy-pasting an existing `*_lora_gui.py` as your starting point, because each bug only surfaces later, in a scenario a quick manual test won't hit:

1. **Logging paths** — an empty `logging_dir` reaching the runtime TOML silently becomes a filesystem-root path on the backend.
2. **Training-mode round-trip** — if the new trainer supports both LoRA and Full Fine-Tuning, `training_mode` must be persisted in the runtime TOML and correctly re-inferred when loading an older TOML that lacks it. Get this wrong and reloading a saved/failed full-finetune run silently retrains it as LoRA instead, with no error shown.

Update `AI_TRAINER_GUARDRAILS.md` with a new guardrail (same format: Rule / Why this exists / Required implementation pattern / Regression check) any time you fix a bug in this codebase that a future "add a new model" pass could plausibly reintroduce.

## Architecture map

- `gui.py` — builds the **unified UI** (`musubi_tuner_gui/unified/`, see below) by default; `python gui.py --classic` instead mounts each trainer's own `*_tab()` function, grouped as **Image Models / Video & Audio Models / Tools / Version History** (nested `gr.Tabs`; Gradio renders tab children lazily). The unified registry (`unified/registry.py`) is the source of truth for which models are live.
- `musubi_tuner_gui/image_models_gui.py` — the **spec-driven** trainer for the newer models: Qwen-Image 2.1, ERNIE-Image, Mage-Flow (T2I + Edit), HiDream-O1 and Kandinsky 6 (video+audio). Each model is one `ImageArchSpec` (scripts, `ModelPath`s, `ExtraOption`s, cache-argument builders, validation hook, defaults); the UI, save/load, presets, runtime TOML and command building are shared. **To add another image/video model, add a spec here** rather than copying a `*_lora_gui.py`. Components are registered by key (`reg()`) and the tab build asserts the registered keys equal `param_keys(spec)`. Tests: `tests/test_image_models_gui.py`.
- `musubi_tuner_gui/preset_library.py` — the **⚡ GPU preset picker** shown under every trainer's configuration bar. Presets live in `<install root>/Training_Presets/<Model>_Training_Configs/{LoRA_Training,Fine_Tuning_Training}/<GPU>_GB_GPUs_<measured peak>_GB*.toml` (`preset_roots()` also reads `<install root>/<Model>_Training_Configs`, where older releases kept them); `MUSUBI_PRESETS_DIR` overrides both. *Apply Preset* writes the path into the tab's config dropdown and then runs that tab's own Load handler (`PresetLibrary.bind`). Shipped presets are read-only: Save refuses to overwrite files inside `*_Training_Configs` (`is_shipped_preset`).
  The shipped tier presets are produced by the VRAM lab in `<install root>/dont_upload/vram_lab/` (not shipped): `measure.py` runs a preset through the owning tab's own print-command path and samples `nvidia-smi` every 100 ms (it waits for an idle GPU 0, writes fresh-cache measurements into a run-specific folder, trains from one cache folder per resolution / frame count — `cache_dir_lab_<W>x<H>[_f<frames>]` — because training loads every `*_<arch>.safetensors` in its cache folder and image cache files are named by the *source* image size, so a shared folder silently reuses or mixes other resolutions' latents, and treats 15 s at the card's total as a WDDM spill/OOM); `autotune.py` searches, per tier, the least block swap of each quality candidate that stays under `tier - 1.5 GB` (a candidate can carry its own `max_swap` and `skip_swaps` where the backend's offloader modes differ) and writes the preset, superseding any older preset of that tier; `make_jobs.py` defines every model's quality ladder and cache options; `queue_runner2.py` runs jobs from `queue2/` one at a time; `make_readmes.py` writes each folder's README table. The lab reads and writes the presets in `<install root>/Training_Presets/` (`PRESETS` in each script; `jobs/*.json` `out_dir` and `tier_report.jsonl` paths point there); the server copy keeps the older `<root>/<Model>_Training_Configs` layout, which `pull_remote_results.py` maps onto `Training_Presets`. `fix_headers.py` runs first, after every pull, because the pull restores the server's files. It normalizes the description lines and caps checkpoint saving at every 25 epochs, keeping only the newest training state. The V34 demo bases saved every epoch for 200 epochs, full fine-tuning with its optimizer state. On a multi-GPU Linux machine, `queue_worker.py --gpu N` (one per GPU) claims jobs from `queue_multi/` atomically (`LAB_GPU` pins the trainer, its caches and the sampling to that GPU; jobs can require downloaded model bundles and free RAM), and `pull_remote_results.py` copies the server's presets and tier records back (folders measured on the server are mirrored; folders measured here only take the tiers the server re-measured). Stop a queue job only with `stop_job.sh <queue name>`: it stops the autotune before its measure and training processes, so a stopped step is never recorded in the job state as a failed configuration. `release_held.sh` moves RAM-heavy jobs from `queue_hold/` into the queue one at a time, because a worker checks free RAM only when it claims a job. After a change that affects every preset (DoRA in the LoRA presets, a library upgrade), `verify_presets.py queue [--fresh-cache] [--kohya-files JSON]` / `work --gpu N` / `report [--write]` re-measures every shipped preset as shipped (kohya FLUX.1 presets through `kohya_smoke.py`; a worker claims a job only with `--min-free-gb` free RAM and prefers the model with the fewest running jobs; `--fresh-cache` re-encodes the caches with the current libraries and removes them afterwards). A state file copied from another machine is reused as long as its results name the GPU they were measured on (`gpu`/`platform`/`peak_offset`). Linux reads 0.37-0.47 GB less than Windows for identical runs (RTX A6000 vs RTX 5090), so `autotune.py` adds a 0.5 GB Windows allowance to Linux measurements (`LAB_PEAK_OFFSET_GB`); each preset names the GPU it was measured on. Never run other GPU work (tests, GUI training) while the queue measures. To keep tests on the CPU set `CUDA_VISIBLE_DEVICES=-1`: an empty value hides nothing on Windows (PowerShell deletes the variable; from bash torch reports 0 devices until CUDA initializes, then sees every GPU, so CUDA-gated tests still run on GPU 0).
- `musubi_tuner_gui/class_tab_config_manager.py` — `TAB_DEFAULT_FILES` is the single registry of tab name → defaults TOML; add new tabs there only.
- `musubi_tuner_gui/*_lora_gui.py` — one file per trainer (e.g. `qwen_image_lora_gui.py`, `wan_lora_gui.py`, `zimage_lora_gui.py`, `modern_image_lora_gui.py` for Ideogram 4 + Krea 2). Each defines the tab's UI, a `train_*_model()` function that builds the launch command and writes the runtime config TOML, and `open_*_configuration()` / `save_*_configuration()` for the Load/Save buttons.
- `musubi_tuner_gui/common_gui.py` — shared infra, including `SaveConfigFile()` (💾 Save button, hand-managed presets) and `SaveConfigFileToRun()` (the actual runtime TOML written to `output_dir`, the one passed to the backend via `--config_file`). These two paths have different exclusion rules — check both when changing what a trainer persists. The backend reads runtime TOML values without argparse conversion, so their types matter (Guardrail 15). Importing the package runs `toml_compat.install()` (`musubi_tuner_gui/__init__.py`): toml 0.10.2's own string writer produced invalid TOML for any path containing `\x` (`C:\Users\xavier\...`).
- `musubi_tuner_gui/full_finetune_gui.py` — shared LoRA-vs-Full-Fine-Tuning helpers used by FLUX, FLUX.2, FLUX Klein, Qwen Image, Z-Image, Ideogram 4, and Krea 2. LTX 2.3 reuses its validation (`normalize_image_training_parameters`) and the round-trip helpers for its own Full Fine-Tuning mode (`ltx2_train.py`: dense BF16, fused Adafactor, trainable block-swap ring, and an optional post-training `ltx2_merge_fft_to_model.py` step that turns the transformer-only checkpoint into an inference-ready bundle; tests in `tests/test_ltx2_full_finetune_gui.py`). Wan and MiniMax H3 don't use it: Wan's full-finetune mode is disabled in the UI (there is no full-DiT Wan script), and MiniMax H3 has no full-finetune script upstream.
- `musubi_tuner_gui/minimax_h3_lora_gui.py` — MiniMax H3 T2VA/FL2VA/Ref2VA video+audio LoRA tab, modeled on the LTX-2 tab (canonical `MINIMAX_H3_PARAM_KEYS` list, `prepare_minimax_h3_workflow` builds latent-cache → TE-cache → train commands). H3 specifics worth knowing before editing: dataset `batch_size` is hard-fixed to 1; frame counts must be 17n+5 (released 124-345); FP8 flags are rejected by the backend (ConvRot INT8 is the quantization path, pre-quantized files auto-detected); the guidance loss (`h3_guidance_loss_scale`, default-on at 4.0) needs an uncond probe cache that the tab auto-writes during TE caching via `--uncond_output`; teacher matching flips the *latent* cache task to `fl2va` while TE caching and training stay `t2va`. Tests: `tests/test_minimax_h3_gui.py`.
- `musubi-tuner/` — the SECourses fork of kohya-ss/musubi-tuner (own git repo: `origin` = FurkanGozukara/musubi-tuner, `upstream` = kohya-ss). As of V35 it is upstream 0.3.6 + dev, plus Qwen-Image 2.1 (PR #1145), ERNIE-Image (PR #934), Mage-Flow (sdbds PR #1010), Kandinsky 6 (AkaneTendo25 `kandinsky-6`), the INT8 ConvRot cuBLAS backend (#1155), the offloader record-stream fix (#1150) and corrupted-cache handling (#1088); fork-only additions include Mage-Flow activation CPU offload (`mage_flow/model.py`, same scheme as Qwen-Image) and HiDream-O1 `--freeze_text_embeddings` for full fine-tuning (the resident 0.6B-parameter token table's update otherwise peaks at 15.5 GB at any resolution), HiDream-O1 keeping its unused vision encoder on the CPU in t2i block-swap runs, and the resolution-aware latent caches of Guardrail 13 (`--skip_existing` re-encodes caches made for another bucket; video training ignores clips cached for another resolution / frame count). Found while measuring the V35 presets: the LTX-2 loader loads only the tensors of the transformer variant it builds and, with block swap, keeps dynamically quantized weights on the CPU (`ltx2_model_loading.py`); FLUX.2 `blocks_to_swap` reaches every swappable block (`Flux2.split_blocks_to_swap`); Ideogram 4 brings the hidden state back after activation-offloaded blocks; Kandinsky 6 latent caching takes `--vae_tiling_memory_gb`; MiniMax-H3 resets the standard block swap after its no-grad guidance/teacher forwards. LTX-2 Gemma text caching loads the FP8 Linear weights straight to CPU RAM, computes only the last position's logits and masks in place in the per-token RMS feature extraction; together these took caching from 13.3 to 10.8 GB (nvidia-smi, Windows-equivalent). `--low_vram_text_encoding` (GUI: *Low-VRAM Text Caching*) moves the embedding table, the projection and the connectors to the GPU one at a time: 5.3 GB, bit-identical caches (`base_encoder.enable_low_vram_text_encoding`). The Z-Image VAE runs its mid-block attention in 4096-row query chunks (`ATTENTION_QUERY_CHUNK`): its single 512-channel head has no fused SDPA kernel, so 1536 px latent caching reserved 19.7 GB, now 8.3 GB. `w8a8_optimization_utils._int_mm_allow_small_m` pads INT8 GEMM rows to a multiple of 32 for a row-major right-hand side, which cuBLASLt on Ampere requires. The fork keeps its own datasource classes in `dataset/image_video_dataset.py` (loss masks, LTX-2 references/guides); when merging upstream dataset changes, port them into those classes (see the V35 merge commit for the DecodedAudio / item-extras / skip_broken pattern). LTX-2 training-time sampling loads the text connectors, VAE and audio models with `ltx_2/loader/sft_loader.in_process_checkpoint_loader()` (plain file reads): safetensors 0.8 cannot map the single-file checkpoint a second time while the training DiT holds tensors mapped from it (CUDA open: "invalid python storage", CPU open: process crash), which stopped every LTX run with samples at its first sample. Training samples run with the LoRA network in eval mode (no LoRA dropout) and call the trainers' `on_before/after_sample_images` hooks in both training loops (`training/training_loop.py`, `trainer_base.py`); a step is sampled once; Krea 2 samples use an empty negative prompt when CFG > 1 (as Krea's sampler), and a bare `--n` in a prompt line is the blank negative `" "` (the GUI writes `--n ` last and prompt lines are stripped). Backend tests: `PYTHONUTF8=1 PYTHONPATH=src python -m pytest tests -c pyproject.toml --rootdir .` from `musubi-tuner/` (UTF-8 mode matters on Windows: some tests decode subprocess output). The suite runs CPU-only with `CUDA_VISIBLE_DEVICES=-1`. Upstream's Wan `T5EncoderModel` evaluated `torch.cuda.current_device()` as a default argument, so importing any Wan module needed a GPU; the fork resolves it in the constructor.
  The vendored training backend holds the actual training scripts, argparse setup, `read_config_from_file`. Unknown TOML keys are harmless there — they become unused `argparse.Namespace` attributes and are never read (see `musubi-tuner/src/musubi_tuner/training/parser_common.py::read_config_from_file`). This is why it's safe for the GUI to persist GUI-only bookkeeping fields (like `training_mode`) into the runtime TOML.
- `tests/test_full_finetune_gui.py` — the relevant suite for anything touching LoRA/full-finetune mode switching or config save/load round-tripping.

Not currently mounted in `gui.py` (present but dormant — still exercised directly by tests, so keep them working when changing shared helpers): `flux2_lora_gui.py` and `flux_klein_lora_gui.py`'s own tab-building functions are superseded by the unified `flux_lora_gui.py` tab (which handles both families via a `model_family` selector), but their `train_*`/`open_*`/`save_*` functions are still imported directly by `tests/test_full_finetune_gui.py`, and `flux_klein_lora_gui.py` still aliases `flux2_lora_gui.py`'s load/save functions. `lora_gui.py` (a legacy HunyuanVideo LoRA trainer) is fully dead, unmounted, and untested — don't build on it.

## Unified UI (`musubi_tuner_gui/unified/`)

- `app.py` builds five tabs: 🖼️ Image / 🎬 Video / 🔊 Audio Models, 🧰 Tools, 📜 Version History. Each model tab is one `Workspace` (`workspace.py`): step cards (base model → LoRA / Fine-Tuning → GPU preset), model card with tips (`hints.py`), settings sections, Start / Stop / Print Command and the live monitor. A trainer module that fails to import only removes its models; a category left without any shows an error card instead of stopping the app. The open tab is remembered in `ui_state.json` (`last_category`) only from selects that carry the browser's user activation (`USER_ACTION_JS`: Gradio itself selects the first tab when a page opens) and a load handler re-selects it; `remember_selection` never writes it (every workspace re-applies its selection on page load). `--headless` drops the 📂 / 📄 browse buttons (no file dialog on a server).
- Trainers are not re-implemented. `legacy_tabs.py` lists the 13 musubi trainer modules and `backends.py` calls each module's own `*_gui_actions` (load, save, print command, train) with values in the module's positional order; FLUX.1 and SDXL run on kohya sd-scripts through `kohya_backend.py`. `registry.py` maps every model the user sees (`ModelEntry`: category, icon, modes, preset folders, fixed variant values such as the FLUX.2 family) to a backend.
- `legacy_schema.json` holds every trainer's settings (keys in positional order, labels, defaults, choices, bounds), recorded by building each classic tab headlessly, plus `arg_types`: the argparse type / nargs of every setting the training scripts read (`tools/trainer_arg_types.py` captures each script's real parser from its own `main()`, CPU only). **Regenerate it after changing a trainer's settings or pulling training-script changes into the fork:** `venv\Scripts\python.exe tools\generate_unified_schema.py`; `tests/test_unified_ui.py::test_schema_matches_the_trainer_modules` fails while it is stale. `schema.py` places keys into sections (`SECTION_KEYS`, `ADVANCED_KEYS`, `LORA_ONLY_KEYS` / `FULL_ONLY_KEYS`); unlisted keys are placed by name.
- Presets (`presets.py`): shipped presets are read-only; user presets are saved by name to `<install root>/user_presets/<model>/` or to any full path, with a `preset_*` metadata header that `identify_preset` uses for the guardrails (a preset of another category is refused, another model or training type is switched to). Last selections live in `user_presets/ui_state.json` (read and written under one lock; a damaged file is ignored, never fatal). A preset that cannot be read is refused when the user picks it (selector and settings stay as they were) and replaced by the defaults, and forgotten, when it was only remembered. `ui_state.json`'s GPU tier only applies where the model offers it (`offered_tier`); the training type of a shipped preset comes from the folders below its `*_Training_Configs` folder, never from the install path; kohya_ss DreamBooth configs (no LoRA keys) load as Fine-Tuning; a name such as `my run.toml` is a preset name, and Load finds a name by the same cleaning Save used. Tests must set `MUSUBI_USER_PRESETS_DIR` so they never write the real state file.
- Values (`values.py`): the trainers load the runtime TOML with `parse_args(namespace=...)`, which converts nothing, so a `1.0`, a `"1e-4"` or a quoted path would reach the training code as written. Every value is converted to its argparse type and paths are cleaned (quotes, padding, line breaks, `/` vs `\`, `%VAR%`, `~`, `file:///`; Hugging Face repo ids and URLs stay as typed) in `Backend.coerce`; `Backend.check` lists unusable input by label for Start / Print Command; `enforce_trainer_types` wraps `common_gui.SaveConfigFileToRun` during unified runs, so classic-tab quirks cannot change types (Qwen Image collapses list options to their first item). Whole-number settings read `10,000` as ten thousand, decimal settings read `1,004` / `0,0001` as decimal commas. Multi-path settings (`base_weights`) use the classic syntax: one per line or `;`, or several on a line with quotes around paths with spaces (an unquoted line splits only where another absolute path starts); the UI shows them that way. Text of several lines is never cleaned as one path (kohya's Sample Prompts takes prompt text). A loaded value is the classic loader's, except path lists a classic loader joined with plain spaces (taken from the file). Blank is valid where 0 is the default or the trainer's own default is None (Wan reads a saved 0 back as blank there); `schema.ZERO_MEANS_UNSET` settings write 0 as "not set" (Max Timestep 0 would train without noise) and `schema.ARG_TYPE_OVERRIDES` records where a TOML value means something else than the command line (Wan's `timestep_boundary` ≤ 1.0 is a fraction). Whole-number settings (`Backend.whole_number`: int arguments, classic `precision=0` numbers, the classic modules' `*_INT_KEYS` and `schema.WHOLE_NUMBER_KEYS` counts such as ports and batch sizes) read `18,343` as eighteen thousand and refuse fractions; `lr_warmup_steps` / `lr_decay_steps` stay a fraction only below 1 (musubi reads any float as a ratio). Save refuses what `Backend.check_values` reports (a classic save would store it changed). `tests/test_unified_presets_roundtrip.py::test_messy_input_survives_save_load_and_the_ui` fuzzes every setting of every model (`UNIFIED_FUZZ_SEEDS=40` for a deeper run). Mode switches without a preset apply the classic tabs' mode recipes (`_mode_recipe`: LTX 2.3 fine-tuning, Ideogram 4 block-swap limit). Tests: `tests/test_unified_values.py`, `tests/test_unified_runtime_toml.py` (every model and training type, messy input, real runtime TOML checked against argparse).
- Datasets (`dataset_tools.py`): Start builds the dataset TOML with each trainer's own generator and hands it over through `generated_toml_path`. In folder mode `generated_toml_path` and `dataset_config` are cleared first and `generated_toml_path` is never saved in a preset: the classic train code reuses that file whenever it exists, which trained an old folder. When `prepare_dataset` built the run's TOML itself (audio clips, mixed folders) the run switches to "Use TOML File" (`_hand_over_dataset`), so the classic train cannot regenerate a different one. 🔍 Check dataset (`dataset_inspector.py`) walks the folders (or a dataset TOML's `[[datasets]]` / kohya `[[datasets.subsets]]`) with the trainers' own rules: musubi's media extensions and exact-stem captions (strict UTF-8, as the trainers read them), its control-image pairing (`photo.png` -> `photo.png`, `photo_0.png`, …; longest name first; any other text after `photo_` stops caching), which generator owns a control folder (`control_settings`: Krea 2 / Ideogram 4 / Z-Image never), sd-scripts' `<repeats>_<class>` folders and regularization images for kohya, the image size as stored (EXIF rotation is ignored by the trainers) and a decode of every probed file. It renders stat cards, problems with example files, a folder table and distributions, and gallery previews (edit pairs side by side, a video's first frame, an audio waveform) cached in `%TEMP%/secourses_dataset_previews` (at most 400 files, written atomically, with a time budget). Tests: `tests/test_unified_datasets.py`. Folders with images and videos also train their images (Wan, LTX 2.3 video mode, Kandinsky 6; the classic generators keep only the videos); MiniMax H3 is video only; LTX 2.3 audio mode uses audio clips and the audio of videos (extracted with PyAV to WAV under `<cache>/extracted_audio`, captions copied; never a sub-folder of the dataset folder itself, which the video generators would skip). Tests: `tests/test_unified_datasets.py` (tiny real media from `tests/media_fixtures.py`).
- Training (`runner.py`): `TrainingRunner` replaces each module's executor, parses tqdm / epoch / checkpoint lines into a bounded snapshot (≤480 chart points, last 600 log lines), finds the run's GPU from nvidia-smi per-process bus IDs and writes the full log to `logs/training_runs/`. `metrics_hook.py` (loaded by `sitecustomize.py` when `SECOURSES_LIVE_METRICS=1`) adds the optimizer's live `lr=` to the steps bar. `monitor.py` polls the runner from the browser through `gr.HTML(server_functions=...)`; it closes a stop question once no run is active and keeps the latest download log until its box is on the page (Model Files is not rendered while collapsed). `downloads.py` marks a download stopped before killing it, so its log ends "stopped", not with the kill's exit code.
- Performance rules (each Gradio 6.30 update walks the whole page on the client and a workspace has ~200 settings): no `gr.Timer` (one tick costs ~0.7 s of main-thread time here); show and hide settings with CSS from `data-*` attributes on the workspace root (`Workspace.generated_css`), never with `visible=` updates (the Download row follows `data-dl`; the banner and the preset description hide while empty with `:has()` rules); send only changed values (`Workspace.emit` diffs against a per-session mirror); give events `show_progress_on=[sink]` and minimal inputs. `queue=False` events cannot show `gr.Info` / `gr.Warning` toasts. One session's events run one at a time (`Workspace.session` lock); model / training type / tier / preset selectors use `trigger_mode="always_last"` (the default drops a second quick click); the state JSON carries a `seq` so every switch re-applies the rule attributes; a no-change result must name one of the event's own outputs (`emit` does). There is no `demo.unload` hook: mirrors are an LRU of `MAX_SESSIONS`. Sliders record user edits with `.input` and `trigger_mode="always_last"`, never `.change` (it also fires for every value a switch sends: one request per slider while the switch renders). The ⚡ VRAM panel (`vram_advice.py`) compares the fields in `vram_advice.WATCHED_KEYS` with the values of the last load (stored per session by `apply` and `restore`) and the preset's measured peak from its file name; it sticks to the bottom of the page, which needs `.gradio-container { overflow: clip }` (Gradio's `hidden` disables every `position: sticky`). Gradio 6 wraps consecutive fields of a row in a `.form` box and resets their min-width to 0: `unified.css` restores it for `.check-grid` / `.field-grid`. Tests: `tests/test_unified_vram.py`. A `gr.Number` emptied by the user sends `null`, but one emptied without an input event keeps its last value: `STATE_JS` refills required numbers on blur (and fires `input`) so the screen and the server agree.
- Value links (`links.py`): the unified UI does not run the classic tabs' Gradio events, so a classic `.change` / `.input` handler that sets another setting's value must be mirrored as a `Link` (HiDream-O1 model type → checkpoint, noise schedule, CFG; HiDream task → control images; Mage-Flow Edit → its own checkpoint; Wan FP8 Base → FP8 Scaled; Wan task → compile residency; Klein version → sample steps / guidance; frame counts rounded to each VAE's grid). The workspace records the trigger and follows its links in one handler; a link also runs at load time when the model entry fixes its trigger, or sets it by default without a preset. A model-file link switches between variant files by name (next to the current file or in the model folder) and clears the path when the target file is missing, never training the other variant's checkpoint. Tests: `tests/test_unified_links.py`.
- 🏆 Best Checkpoint Finder (`checkpoint_finder.py`, scoring in `musubi_tuner_gui/best_checkpoint/`): image and video categories only (`CF.available`). Its settings (on/off, subject, prompts, seeds per prompt, leakage check) are remembered per category in ui_state.json (`best_checkpoint`) and saved with a user preset as the `preset_best_checkpoint` header line (JSON in a TOML string, `P.write_metadata_header(extra=...)`); a user preset the user loads applies them (`apply(finder_from_preset=True)`), a shipped preset keeps the current ones, and kohya loads ignore every `preset_*` key. Start calls `CF.prepare_run` after the `_last_run` autosave (which keeps the user's own sampling): it needs Save Every N Epochs or Steps, writes `<output_dir>/best_checkpoint/<output_name>/{sample_prompts.txt, settings.json}` (one line per prompt and seed with `--d`; the user's own sample prompts follow and are not scored), sets Sample Prompts, Sample Before Training and the sample interval to the save interval, and passes a `runner.AfterStep` to `RUNNER.start_job(after=...)`. When the training process exits 0 the runner runs `python -m musubi_tuner_gui.best_checkpoint.worker` as the `score` stage (shown only for such runs; Stop ends it; its failure never fails the training), then reads `report.json` into the snapshot's `result` (the dashboard's 🏆 card; its button opens the section's 📊 Show results). 🔍 Analyze runs the worker alone (`RUNNER.start_after_step`). Edit models (control images required) skip it. The worker indexes musubi / sd-scripts sample names (`samples.py`: epoch or step points, `e000000` = base model), scores with YuNet + SFace (OpenCV Zoo), DINOv2-base and SigLIP2-so400m (downloaded on first use to `<install root>/Training_Models_Checkpoint_Finder`, `MUSUBI_FINDER_MODELS` overrides) and ranks with `ranking.py` (thresholds from `dont_upload/best_checkpoint_research`). Tests: `tests/test_best_checkpoint.py`, `tests/test_unified_ui.py::test_best_checkpoint_finder_*`.
- LoRA / DoRA (`adapter.py`): Adapter Type is not a trainer setting. It is appended after each backend's positional specs (`is_synthetic`), folded into Network Arguments (`use_dora=True`) for save, print command and Start in LoRA mode, and read back from them on load, so presets stay plain trainer configs. DoRA is the input-axis form (Guardrail 18; musubi `DoRAInputModule`, sd-scripts `networks/dora.py`), which ComfyUI and SwarmUI load like a LoRA; SECoursesAudioTools' `musubi_lora_keys.py` registers the trainer's layer names that ComfyUI V92 otherwise skips (Qwen-Image 2.1 MLP halves, Z-Image q / k / v, every HiDream-O1 layer). Network Arguments for DoRA: `use_dora=True` (input axis), `dora_axis=output` (PEFT `lora_magnitude_vector`, needs conversion for ComfyUI), `dora_detach_norm=True` (no gradient through the column norm, DoRA paper section 4.3: about half of DoRA's extra time), `dora_scale_lr_ratio=<x>` (learning rate of the magnitudes relative to the LoRA matrices). Eager DoRA is bound by op dispatch (`dont_upload/vram_lab/dora_overhead_bench.py` measures and profiles it), so keep the per-layer path free of no-op casts and views. Tests: `tests/test_unified_adapter.py`, `tests/test_kohya_dora.py`.
- Adding a model: build the trainer as usual (an `ImageArchSpec` or its own module), register it in `legacy_tabs.py` and `registry.py`, regenerate the schema, mirror any handler that sets one setting from another in `links.py`, add tips to `hints.py` (every number must come from a preset, its README, the defaults or the code: `tests/test_unified_tips.py` checks block-swap limits, VRAM figures and models without presets) and run `tests/test_unified_ui.py` and `tests/test_unified_tips.py`.

## Running tests

```
venv/Scripts/python.exe -m pytest tests/ -q
```

Keep the full suite green. When changing `full_finetune_gui.py` or any `*_lora_gui.py`'s save/load logic, also sanity-check that the actual Gradio tab still builds without error — most trainer functions are only exercised as plain Python calls in the test suite, not through real Gradio component construction, so wiring mistakes (bad `.then()`/`.change()` inputs or outputs, references to undefined components) can slip past pytest alone:

```python
import gradio as gr
from musubi_tuner_gui.<trainer>_lora_gui import <trainer>_lora_tab
with gr.Blocks():
    <trainer>_lora_tab(headless=True, config={})
```

For anything touching config Load/Open behavior specifically, prefer verifying live in the running app (`python gui.py`) over trusting the tab-build check alone — some bugs (like the numeric-bounds gotcha in Guardrail 2) only appear once real Gradio event round-trips run in a browser, not from constructing the component tree.
